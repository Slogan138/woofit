# 21 · 세션 수명

> **개선** · 폰 · 워치 · [PRD §4 F-3 · F-14](../PRD.md) · 결정 근거 [D14](../PRD.md#11-확정-사항)
> **새 기능이 아니다.** "진행 중"이 언제 끝나는지를 정하지 않아 생긴 버그들을 뿌리에서 막는 일이다.

## 왜 지금인가

실사용에서 나온 증상 셋이 전부 같은 원인이었다.

| 증상 | 직접 원인 | 뿌리 |
| --- | --- | --- |
| 손목을 올리면 휴식 타이머가 리셋됐다 | 옛 컨텍스트 병합이 진행 중 세션을 중단시킴 | 끝나지 않은 세션이 남아 있었다 |
| 워치에서 휴식 중 앱이 내려간다 | 이어받은 세션은 `HKWorkoutSession` 을 안 켠다 | 그래서 앱이 죽고 또 세션이 남는다 |
| 시뮬레이터를 켜니 예전 세션이 열려 있었다 | 복원이 진행 중 세션을 나이 제한 없이 집는다 | 같음 |

첫 번째는 [fix/rest-timer-reset](../../) 에서 병합 규칙을 좁혀 막았다. 그건 증상을
막은 것이고, **세션이 왜 남는지는 그대로다.**

`inProgress` 를 빠져나가는 길은 `finish()` 와 `abandon()` 둘뿐이다. 둘 다 앱이 살아 있어야
불린다. 그런데 이어받은 세션에서는 **워치 앱이 휴식마다 죽는다.** 그래서 이어받기를 쓸
때마다 하나씩 남는다.

## 무엇이 잘못됐나

애플 운동·음악 앱에서 "진행 중"은 **기기에서 살아 있는 동안만** 존재한다. 소리가 나고
있거나 `HKWorkoutSession` 이 돌고 있는 동안이고, 죽으면 그 상태도 사라진다. 그래서
"며칠 전 운동이 복원된다"가 구조적으로 불가능하다.

우리는 그것을 **디스크에 영속되는 데이터**로 만들었다. `stateRaw = "inProgress"` 는
아무도 안 지우면 영원히 남고, 주인도 만료도 없다.

세션 복원(F-3)은 "운동 중에 앱이 죽어도 이어서 하려고" 넣은 장치다. **워치 앱이 매 세션
죽는 현실에서 그 장치는 실제로 필요하다.** 없앨 것이 아니라, 돌아오지 않은 세션을
끝내는 경로를 만들어야 한다.

### 애플은 자동으로 끝내지 않는다

운동을 마치고 종료를 안 누르면 애플 운동 앱은 계속 돈다. 경과 시간이 올라가고 심박을
계속 재고 배터리를 먹는다. 대신 **잊을 수 없게 만든다** — 손목을 올릴 때마다 그 화면이
뜨고, 움직임이 멈춘 걸 감지하면 종료할지 묻는다.

우리는 조용히 정리해도 된다. **세트 기록이 이미 영속돼 있어 잃는 것이 "진행 중" 표시뿐**
이기 때문이다. 애플은 세션을 끝내는 순간이 곧 저장 시점이라 함부로 끝낼 수 없다.

## 범위

**하는 것** — 워치 수명 연장, 남은 세션 정리, 무기록 안내.

**하지 않는 것**

- 폰을 리모컨으로 격하 — 루틴 편집·기록 수정(F-15)·추이(F-10)는 폰이 주인이어야 한다.
  주인은 **세션마다** 정해지는 것으로 충분하다(음악 앱과 같은 모델)
- `UserNotifications` 도입 — 운동 세션이 켜져 있으면 앱이 살아 있고 손목을 올릴 때마다
  보인다. 앱 안의 배너와 햅틱으로 족하다. 권한을 하나 더 물을 이유가 없다
- 사용자에게 복원 여부를 묻는 다이얼로그 — 헬스장에서 앱을 열 때마다 뜨면 F-3 의
  "성공은 1탭"이 무색해진다. 잃는 데이터가 없으니 조용히 정리한다
- 새 저장 프로퍼티 — 마지막 활동은 `recordedAt` 최댓값에서 유도한다(§7 CloudKit 제약)

## 설계

### 마지막 활동 시각

```swift
/// 이 세션에서 마지막으로 무언가 일어난 시각. 기록이 하나도 없으면 시작 시각이다.
var lastActivityAt: Date { allSets.compactMap(\.recordedAt).max() ?? startedAt }
```

**새 필드를 만들지 않는다.** 저장 프로퍼티를 늘리면 CloudKit 제약(기본값·옵셔널)과
동기화 payload 를 함께 손봐야 하는데, 필요한 값이 이미 기록 안에 있다.

### 왜 경과 시간이 아니라 무기록 시간인가

실측 평균 세션이 **50분**이다. 경과 시간 60분을 기준으로 삼으면 종목이 하나 더 붙거나
기구를 기다린 날마다 걸린다. **정상적으로 운동하는 중에 서너 번에 한 번꼴로 알림이 뜨고,
그런 알림은 몇 주 안에 무시하게 된다.**

세트 간격은 보통 1~3분이다. "마지막 기록 후 20분"은 운동 중에는 거의 걸리지 않고
자리를 떴다는 것만 정확히 집는다. 애플의 종료 알림도 시간이 아니라 움직임으로 판단한다.

| 신호 | 임계값 | 동작 |
| --- | --- | --- |
| 마지막 기록 후 | 20분 | 햅틱 한 번 + 세션 화면 배너 "아직 운동 중인가요?" |
| 마지막 기록 후 | 45분 | 배너에 `계속` · `중단` 선택지 |
| 앱을 다시 열었을 때 | 날이 바뀜 | 복원하지 않고 중단으로 정리 |

첫 세트를 기록하기 전에는 시작 시각이 기준이 된다(준비운동이 길면 배너가 뜰 수 있으나
배너 한 줄이라 방해가 크지 않다).

날짜 기준을 쓰는 이유는 시간 기준(예: 6시간)이 자정 넘어 운동한 경우를 어중간하게
자르기 때문이다. **"오늘 시작한 세션인가"가 사람이 판단하는 기준과 같다.**

### 복원은 가장 최근 하나

```swift
// 지금 — 정렬이 없어 보통 먼저 저장된(오래된) 쪽이 나온다
var descriptor = FetchDescriptor<WorkoutSession>(predicate: #Predicate { $0.stateRaw == inProgress })
descriptor.fetchLimit = 1
```

정렬을 넣고, 만료된 것은 그 자리에서 중단으로 확정한 뒤 후보에서 뺀다.

### 새 세션을 시작하면 정리한다

`SessionCoordinator.start` 와 `WatchSessionCoordinator.start` 는 지금 기존 진행 중 세션을
건드리지 않는다. 지금까지 문제가 안 보인 것은 **동기화가 대신 청소해줬기 때문이다** —
새 세션이 상대 기기에 도착하면 더 오래된 진행 중 세션을 중단 처리한다. 한 기기만
쓰는 경우엔 그 청소가 일어나지 않는다.

정리 규칙은 이미 `SyncMerger.mergeInProgress` 에 있는 것과 같다. **로컬 시작 경로에서도
같은 규칙을 쓴다** — 두 곳에 다른 규칙이 있으면 어느 쪽이 이겼는지 추적할 수 없다.

### 워치 수명 연장

지금은 워치에서 **시작한** 세션만 운동 세션을 켠다. 계획 17 이 복원 경로를 막아둔 것은
며칠 전 세션이 되살아나 **몇 시간짜리 유령 운동**이 건강 앱에 남는 것을 막기 위해서였다.

만료 판정이 생기면 그 조건을 안전하게 풀 수 있다. **살아 있는 세션이면 켠다.**
유령 운동의 전제였던 "며칠 전 세션 복원"이 이제 일어나지 않는다.

앱이 죽었다 살아난 경우에는 **돌던 운동 세션을 되찾는다**(`recoverActiveWorkoutSession`).
새로 시작하면 한 번의 운동이 건강 앱에 둘로 쪼개져 남는다. 애플이 이 경우를 위해
제공하는 표준 경로다(원칙 1).

## 작업 단위

**1단계만으로도 지금 겪는 불편이 사라진다.** 나머지는 그래도 새는 것을 받는 그물이다.

### 1단계 · 워치 수명 연장 (워치)

| | |
| --- | --- |
| `WorkoutSession` | `lastActivityAt`, `isLive(at:)` 계산 프로퍼티 |
| `WatchSessionCoordinator.restoreIfNeeded` | 살아 있는 세션이면 `workoutSessionController.start()` |
| `HealthKitWorkoutSession` | `recoverActiveWorkoutSession` 으로 기존 세션 되찾기 |

### 2단계 · 정리 그물 (WoofitCore + 양쪽 화면)

| | |
| --- | --- |
| `SessionRestore.fetchInProgress` | 최근순 정렬. 만료된 것은 중단 처리하고 건너뛴다 |
| `SessionLifetime`(신규) | 만료 판정과 정리를 한곳에. 복원·시작 양쪽이 같은 규칙을 쓴다 |
| `SessionCoordinator.start` · `WatchSessionCoordinator.start` | 시작 전에 정리를 부른다 |

### 3단계 · 무기록 안내 (WoofitCore + 양쪽 화면)

| | |
| --- | --- |
| `SessionLifetime.nudge(for:at:)` | `.none` · `.asking` · `.offeringEnd` 판정 |
| `SessionRunnerView` · `WatchSetView` | 배너 표시. 45분이면 `계속` · `중단` |
| 햅틱 | 20분 진입 시 한 번. `sensoryFeedback(trigger:)` 로 기존 방식 그대로 |

배너는 **시간이 흐르면 저절로 떠야 한다.** 휴식 타이머와 같은 방식으로
`TimelineView` 를 쓴다 — 타이머를 따로 돌리지 않는다(§9 배터리).

전부 `WoofitCore` 에서 시뮬레이터 없이 돈다. 시각은 인자로 주입한다(`at:` 관례).

| 테스트 | 보장 |
| --- | --- |
| 마지막 기록이 없으면 시작 시각이 마지막 활동이다 | 유도 규칙 |
| 오늘 시작한 진행 중 세션은 살아 있다 | 복원 대상 |
| 날이 바뀐 진행 중 세션은 살아 있지 않다 | 만료 |

| 마지막 기록 후 20분이면 안내, 45분이면 선택지 | 임계값 |
| 19분·44분에는 아직 아니다 | 경계 |
| 기록이 이어지면 안내가 사라진다 | 재진입 |

5. 실기기 — **폰에서 시작해 워치로 이어받은 뒤 손목을 내렸다 2분 후 들어 올렸을 때
   시계 화면이 아니라 세트 화면이 보인다** (F-14 수용 기준을 이어받기에도 적용)

## 주의점

**만료 정리는 삭제가 아니다.** 반드시 `abandon()` 이다. 진행 중 세션을 지우면 그날의
기록이 통째로 사라진다 — 이 앱에서 가장 나쁜 결과다(§8 병합 규칙과 같은 이유).

**`abandon()` 은 휴식 측정을 함께 끝낸다.** 살아 있는 세션을 실수로 정리하면 타이머가
사라진다 — 어제 고친 버그가 정확히 그 경로였다. 만료 판정에 `isLive` 를 통과한 세션은
어떤 경로로도 정리되지 않아야 한다.

**운동 세션을 켜는 조건과 만료 조건은 같은 함수를 써야 한다.** 다르면 "복원은 됐는데
운동 세션은 안 켜진" 또는 그 반대의 조합이 생기고, 실기기에서만 드러난다.

**되찾기는 실패할 수 있다.** 앱이 죽은 지 오래면 운동 세션도 이미 끝나 있다. 그때는
조용히 새로 시작한다 — 되찾기 실패를 오류로 다루면 정상 경로가 막힌다.

## 구현 메모

세 단계를 한 번에 넣었다. 2단계가 없으면 1단계가 유령 운동을 만들고, 1단계가 없으면
2단계가 계속 치우기만 하므로 **따로 배포할 이유가 없었다.**

### 설계에서 바뀐 것

**`restoreIfNeeded` 가 컨트롤러를 인자로 받는다.** 코디네이터가 `WorkoutSessionController`
를 들고 있게 하면 워치 세션과 운동 세션이 각자 수명을 갖게 된다(계획 17 이 피한 구조).
호출부가 넘기는 형태를 유지했다.

**만료 정리를 `SessionRestore` 안에서 한다.** 복원과 정리를 호출부에서 두 번 부르게 하면
한쪽을 빠뜨린 경로가 생긴다 — 폰·워치 코디네이터와 앱 시작·scenePhase·세션 도착까지
호출 지점이 다섯 군데다. 복원을 요청하면 정리는 반드시 함께 일어난다.

**「계속」 상태는 모델에 넣지 않는다.** 화면의 `@State` 로 충분하다 — 앱이 다시 뜨면
다시 물어야 맞고, 상대 기기와 공유할 이유도 없다. 판정 함수는 기준 시각만 받는다.

### 임계값은 설정으로 뺐다

20·45분을 고정값으로 두면 실사용에서 맞는지 확인할 방법이 없다. 설정에서 바꾸거나
끌 수 있게 하고, **폰에서 바꾼 값을 워치로 내려보낸다** — 안내가 실제로 보이는 곳은
손목인데 설정 화면은 폰에만 있다.

저장은 `UserDefaults`, 읽기는 양쪽 다 `@AppStorage` 로 같은 키를 본다. 워치는 받은 값을
그 키에 얹기만 하므로 읽는 코드가 폰과 같다. `0` 은 "사용 안 함"이다 — 켜고 끄는 값을
따로 두지 않는다.

`UserDefaults` 가 없는 키에 `0` 을 돌려주는 것이 함정이다. 그대로 읽으면 **아무도 설정한
적 없는데 안내가 꺼진 채로 시작된다.** `object(forKey:)` 로 존재 여부를 먼저 본다.

### 정리된 상태를 상대 기기로 보내지 않는다

만료로 중단된 세션을 릴레이하지 않는다. **양쪽이 같은 규칙으로 각자 정리하면 수렴하고**,
보내면 "어느 쪽 정리가 이겼는가"를 따져야 한다. 세션 종료 릴레이(F-8)와 달리 여기서는
