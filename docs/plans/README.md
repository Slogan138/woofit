# 작업 계획

기능별 구현 계획. 각 문서는 [PRD](../PRD.md) 의 요구사항 하나에 대응한다.

**파일명 앞 숫자가 개발 순서다.** 정렬 순서와 진행 순서가 같아지도록 붙였다.
파일명의 `F06` 은 PRD 요구사항 번호이고, 앞의 `01` 은 이 순서에서의 위치다.

계획의 상세도는 마일스톤 거리에 비례한다. M1 은 파일·함수 단위까지, M2 는 구조까지,
M3 는 개요까지만 적었다. **M3 는 데이터가 6~10주 쌓인 뒤에야 무엇을 만들지 알 수 있으므로,
지금 상세하게 적어봐야 대부분 틀린다.**

## 왜 이 순서인가

```
01 내보내기 ──▶ 02 가져오기 ──▶ 03 루틴 확인 ──▶ 04 세션 실행 ──▶ 05 다음 종목
                                                                        │
                                            여기서 노트 ↔ 앱 왕복이 닫힌다 ◀┘
                                                        │
                    06 루틴 작성(대안 경로) ◀────────────┤
                    07 직전 기록(화면 통합) ◀────────────┘
```

**01 → 02 를 먼저 하는 이유.** 둘 다 순수 함수라 화면 없이 테스트로 완결된다.
내보내기가 먼저인 것은 그 출력이 곧 가져오기의 입력이라, 왕복 테스트
(export → import → 같은 결과)를 바로 쓸 수 있어서다.

**05 에서 앱이 실제로 쓸 수 있게 된다.** 노트에서 마크다운을 붙여넣어 루틴을 만들고,
세션을 실행하고, 결과를 다시 마크다운으로 뽑는 한 바퀴가 여기서 닫힌다.

**06 루틴 작성이 늦은 이유.** 편집기는 가져오기(02)의 **대안 경로일 뿐 임계 경로가 아니다.**
마크다운 붙여넣기로 루틴을 만들 수 있으므로, 편집기 없이도 앱은 완전히 동작한다.
실사용에서도 노트에서 고쳐 붙여넣는 쪽이 주 경로가 될 가능성이 높다.

**07 직전 기록이 늦은 이유.** 이 기능의 **주 전달 경로인 마크다운 `지난 기록` 열은
01 에서 이미 완성된다.** 07 에 남는 것은 루틴 편집기와 세션 화면에 붙이는 통합 작업뿐이라,
두 화면(04·06)이 존재한 뒤에 해야 한다.

**08 동기화가 M2 의 처음인 이유.** 워치에 루틴이 내려가지 않으면 워치에서 할 수 있는 일이
아무것도 없다. 03·04·05 의 워치 부분도 전부 이것을 전제한다.

## 문서 형식

각 계획은 같은 구조를 따른다.

- **요구사항** — PRD 에서 무엇을 약속했나
- **선행 조건** — 무엇이 끝나야 시작할 수 있나
- **작업 단위** — 체크박스. 이 순서대로 진행
- **파일** — 무엇을 어디에 만드나
- **테스트 계획** — 무엇을 어떻게 검증하나
- **완료 기준** — 언제 끝난 것으로 보나
- **주의점** — 놓치기 쉬운 것

**선행 조건 목록에 나오는 계획 번호는 자기 번호보다 작아야 한다.** 뒤 번호가 목록에
적혀 있으면 순서가 틀렸거나 문구가 잘못된 것이다. 이미 완료된 코드를 가리키는 것이라면
계획 번호가 아니라 타입·함수 이름으로 적는다. 그래야 "저 계획이 끝나야 시작할 수 있나"
하는 오해가 생기지 않는다.

작업하면서 계획이 틀린 걸 발견하면 **계획 문서를 고친 뒤 진행한다.**
계획과 다르게 구현하고 문서를 방치하면 다음 세션이 잘못된 문서를 믿는다.

순서를 바꿔야 하면 파일명 접두사도 함께 바꾸고 이 표를 갱신한다.
번호와 실제 순서가 어긋난 채로 두지 않는다.
