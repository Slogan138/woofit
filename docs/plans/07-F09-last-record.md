# F-09 · 직전 기록 표시

> **M1**(폰) / **M2**(워치) · [PRD §4 F-9](../PRD.md#f-9--직전-기록-표시-폰-워치-m1--m2) · 결정 근거 [D6](../PRD.md#11-확정-사항)

## 요구사항

점진적 과부하는 **"지난번에 성공했는가"** 로 결정된다. 그 정보를 판단하는 자리에 놓는다.
차트가 아니라 한 줄이다.

- **루틴 편집기**(폰) — 종목마다 `지난 기록: 80kg ✅✅✅✅❌(3) · 8월 24일`
- **세션 실행 화면**(폰·워치) — 현재 종목의 직전 기록 유지. 워치는 `지난번 80kg × 5 ✅`
- **루틴 마크다운**(F-06) — `지난 기록` 열. **이것이 주 전달 경로다**
- 완료·중단된 세션에서만 찾는다. 진행 중 세션 제외
- 첫 수행이면 빈 칸. 오류가 아니다

**수용 기준** — 무게를 올릴지 판단하려고 다른 화면으로 이동할 필요가 없다.

## 선행 조건

- ✅ `LastRecord.summary` · `compactSummary`

## 설계 메모

**새로 만들 로직이 거의 없다.** 이 기능은 대부분 통합 작업이다.

호출 시점 주의 — `fetchAll(for:in:)` 은 루틴의 모든 종목을 순회하며 조회한다.
루틴 편집기가 매 렌더마다 부르면 느려진다. **화면 진입 시 한 번 조회해 보관**하고,
세션 기록이 바뀔 때만 갱신한다.

세션 실행 중에는 **현재 세션을 제외**해야 한다. `fetch(normalizedName:in:excluding:)` 의
`excluding` 인자에 진행 중 세션 id 를 넘긴다. (진행 중 세션은 `stateRaw` 필터에서
이미 걸리지만, 중단 후 재개하는 경우를 대비해 명시적으로 제외한다.)

**워치는 조회하지 않는다.** 워치는 세션을 최근 10건만 갖고 있어서 두 달 전 기록을
찾을 수 없다. 폰이 루틴을 내려보낼 때 계산해서 함께 실어 보낸다(F-08).

## 테스트 계획

조회 로직 테스트는 이미 있다. 통합 지점에 대해 추가한다.

| 테스트 | 검증하는 것 |
| --- | --- |
| ✅ 진행 중 세션은 직전 기록에서 제외된다 | 완료 |
| ✅ 공백 표기가 달라도 찾는다 | 완료 |
| ✅ 첫 수행이면 `nil` | 완료 |
| 루틴 내보내기에 `지난 기록` 열이 채워진다 | F-06 통합 |
| 직전 기록이 없는 종목은 열이 빈 칸이다 | 첫 수행 표시 |
| `excluding` 으로 현재 세션을 제외하면 그 이전 기록이 나온다 | 세션 중 조회 |
| `summary` 가 `80kg ✅✅✅✅❌(3) · 8/24` 형식이다 | 표기 |
| `compactSummary` 가 워치 폭에 맞게 압축된다 | 표기 |

## 주의점

- **조용히 망가지는 기능이다.** 종목명 정규화가 어긋나면 직전 기록이 오류가 아니라
  "첫 수행"처럼 빈 칸으로 보인다. 눈치채기 어려우므로 정규화 테스트를 반드시 유지한다.
- 종목명을 바꿀 때는 `rename(to:)` 를 쓴다. `name` 직접 대입은 히스토리를 끊는다.
- `fetchAll` 을 반복 호출하지 않는다. 화면 진입 시 1회.
