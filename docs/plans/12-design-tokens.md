# 12 · 디자인 토큰과 시각 일관성

> **개선** · 폰 · 워치 · 새 기능 아님

## 무엇을 하나

기능은 그대로 두고 **표현만 정리한다.** 새 동작을 만들지 않으므로 PRD 요구사항이 늘지 않는다.
화면 구조도 바꾸지 않는다 — 세션 실행 화면을 재설계하는 건 별도 작업이다.

## 왜 지금인가

화면 21개가 각자 색과 폰트를 직접 지정한다. 지금은 SwiftUI 기본값에 기대어 그럭저럭
일관되지만, 한 곳을 손대는 순간 흩어진다. M3(추이 그래프)는 색을 본격적으로 쓰는
작업이라 그 전에 기준을 세워두는 게 맞다.

## 조사 결과 — 실제로 어긋난 곳

**① 세트 결과에 색 기준이 없다.** `SetResult` 는 `markdownSymbol`(✅ ❌ ⏭)만 갖고 색은
화면마다 즉흥적이다. 같은 "실패"가 `SessionRunnerView` 에서는 `.red` tint 인데
`SessionDetailView` 에서는 이모지만 나온다.

**② 파랑이 두 가지 뜻으로 쓰인다.** `RoutineListView` 의 편집 스와이프, `WatchSetView`·
`WatchNextExerciseView` 의 되돌리기·시작이 전부 `.blue` 다. 강조인지 되돌리기인지
구분되지 않는다.

**③ 주황도 두 가지다.** 휴식 타이머(`RestTimerView`, `WatchRestView`)와 루틴 복제
스와이프(`RoutineListView`)가 같은 `.orange` 다.

**④ 폰트가 10종.** `.caption` 15회, `.caption2` 12회, `.headline` 10회에 더해
`.title3.monospacedDigit()`, `.title2.bold()`, `.subheadline.weight(.medium)` 등이 섞여 있다.
같은 위계인데 다른 폰트를 쓰는 곳이 있는지 확인이 안 된다.

**⑤ 터치 대상 크기 기준이 없다.** `.controlSize(.large)` 가 두 곳에만 있다. 세션 실행
화면의 성공·실패 버튼은 기본 크기인데, 여기가 땀 손으로 가장 자주 누르는 곳이다.

## 원칙

**표준을 따른다(CLAUDE.md 원칙 1).** 자체 디자인 시스템을 짓지 않는다. SwiftUI 의
`Color`·`Font`·`ShapeStyle` 위에 **이름만 붙이는 얇은 층**이다. 시맨틱 색
(`Color.accentColor`, `.primary`, `.secondary`)과 Dynamic Type 을 그대로 쓴다.

**Dynamic Type 을 깨지 않는다.** 고정 포인트 크기를 넣지 않는다. 접근성 요구사항이다(PRD §9).

**색만으로 상태를 구분하지 않는다.** 기호(✅ ❌ ⏭)가 이미 있으므로 색은 보조다.
PRD §9 접근성 요구사항이고, 헬스장 조명에서도 유리하다.

## 완료 기준

1. `swift test` 통과 — 1번이 모델을 건드리므로 테스트가 필요하다
2. `xcodebuild build` 폰·워치 양쪽 통과
3. 색을 직접 지정하는 화면이 남지 않을 것 (토큰 경유)
4. 라이트·다크 모드 양쪽에서 확인
5. **동작이 하나도 바뀌지 않을 것** — 표현만 바꾸는 작업이다

## 주의점

**구조를 바꾸고 싶어진다.** 색을 정리하다 보면 "이 화면은 배치가 잘못됐는데" 싶어진다.
그건 별도 작업으로 남기고 여기서는 손대지 않는다. 섞이면 무엇 때문에 나빠졌는지
되짚을 수 없다.

**실기기에서 봐야 한다.** 시뮬레이터의 색과 실제 화면이 다르고, 워치는 특히 그렇다.
헬스장 조명을 흉내낼 수 없으니 실제로 한 번 들고 가보는 것이 최종 확인이다.
